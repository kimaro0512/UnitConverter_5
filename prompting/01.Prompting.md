# MOM Test (The Mom Test) — 처음 듣는 사람을 위한 설명

프로젝트 코드에는 MOM Test 관련 내용이 없습니다. 말씀하신 **“진짜 문제를 찾기 위해서”**라는 맥락으로 보면, 스타트업·제품 개발에서 쓰는 **Rob Fitzpatrick의 『The Mom Test』(엄마 테스트)** 방법론을 말씀하시는 것으로 이해했습니다. 아래는 그 기준으로 설명합니다.

---

## 1. MOM Test가 뭔가요?

**MOM Test(The Mom Test)**는 아이디어가 좋은지, 사람들이 정말 돈을 낼 만한 **진짜 문제**가 있는지 확인하기 위한 **고객 인터뷰 방법**입니다.

핵심 한 줄:

> **“내 아이디어 어때?”라고 묻지 말고, 상대방의 **과거 행동과 경험**을 물어라.**

소프트웨어의 **단위 테스트(Unit Test)**와는 다릅니다. 코드가 맞는지 검증하는 게 아니라, **문제 정의가 맞는지** 검증하는 방법입니다.

---

## 2. 왜 “엄마(Mom)” 테스트인가요?

책 제목의 비유는 이렇습니다.

- 엄마에게 *“내 앱 아이디어 좋지?”*라고 물으면, 대부분 **“응, 좋아!”**라고 합니다.
- 엄마는 당신을 아끼기 때문에 **거짓말(칭찬)**을 하기 쉽습니다.
- 그래서 **“엄마도 거짓말 못 하게”** 질문을 설계해야 한다는 뜻입니다.

즉, **가까운 사람·친절한 사람·예의 바른 사람**에게도 통하는 질문 방식을 만드는 것이 MOM Test입니다.

---

## 3. MOM Test의 3가지 핵심 규칙

### 규칙 1: 아이디어에 대해 직접 묻지 마라

| 나쁜 질문 | 왜 나쁜가 |
|-----------|-----------|
| “이런 앱 만들면 쓸 것 같아?” | 미래 예측 → 대부분 “응” |
| “이 기능 있으면 좋겠지?” | 상대가 예의상 동의 |
| “얼마면 살 의향 있어?” | 가상의 가격 → 의미 없는 답 |

### 규칙 2: 과거와 현재를 물어라 (미래는 묻지 마라)

| 좋은 질문 | 왜 좋은가 |
|-----------|-----------|
| “마지막으로 ○○ 때문에 고생한 게 언제야?” | **실제 경험** |
| “그때 어떻게 해결했어?” | **실제 행동** (돈·시간 투입) |
| “그 방법의 불편한 점은?” | **진짜 pain point** |

**미래 의향** (“쓸 것 같아?”)보다 **과거 행동** (“지난달에 뭘 샀어?”)이 훨씬 신뢰할 수 있습니다.

### 규칙 3: 상대방의 삶에 대해 물어라, 내 아이디어에 대해 말하지 마라

- 인터뷰 초반에 솔루션을 설명하면, 상대는 그에 맞춰 답합니다 (**편향**).
- 먼저 **문제 상황·습관·비용·감정**을 파고든 뒤, 필요할 때만 아이디어를 짧게 보여줍니다.

---

## 4. “진짜 문제” vs “가짜 문제” 구분법

MOM Test 관점에서 **진짜 문제**는 보통 이런 신호가 있습니다.

| 진짜 문제 신호 | 가짜 문제 신호 |
|----------------|----------------|
| 이미 **돈·시간·노력**을 썼음 | “있으면 좋겠다”만 있음 |
| **구체적인 최근 사례**가 있음 | 추상적 불만만 있음 |
| **대안**을 찾아 쓰고 있음 (엑셀, 수기, 다른 앱) | 아무것도 안 하고 그냥 참음 |
| 문제를 **스스로** 언급함 | 내가 문제를 **제안**해야만 고개를 끄덕임 |

**“진짜 문제를 찾는다”** = “사람들이 이미 고통받고, 대안을 쓰고, 더 나은 해결을 원하는 **패턴**이 반복되는가?”를 확인하는 것입니다.

---

## 5. MOM Test 인터뷰 진행 순서 (실무용)

### Step 1: 대상 정하기
- **잠재 고객** (문제를 겪을 가능성이 있는 사람)
- 친구·가족도 가능하지만, **업무/생활 맥락**에서 실제로 그 문제를 겪는 사람이 더 좋습니다.

### Step 2: 인터뷰 구조 (대략 15~30분)

```
1. 소개 (2분)
   - “아이디어 검증 중이라, ○○ 경험에 대해 듣고 싶어요.”
   - 솔루션 얘기는 아직 하지 않음

2. 문제 탐색 (15~20분)
   - 최근 관련 경험
   - 그때 뭘 했는지 (행동)
   - 얼마나 자주, 얼마나 아팠는지
   - 지금 쓰는 해결책과 불만

3. (선택) 솔루션 힌트 (3~5분)
   - “만약 ○○가 된다면…” 정도만, 반응 관찰

4. 마무리
   - “비슷한 분 소개해 주실 수 있을까요?” (다음 인터뷰)
```

### Step 3: 기록할 것
- **직접 인용**(그 사람 말 그대로)
- **구체적 사건**(언제, 어디서, 무엇을)
- **행동**(무엇을 샀/썼/만들었는지)
- **감정**(짜증, 불안, 당황 등)

---

## 6. 좋은 질문 vs 나쁜 질문 예시

### 나쁜 질문 (피해야 함)
- “단위 변환 앱 있으면 쓸 거야?”
- “이 기능 필요해?”
- “월 5,000원이면 결제할래?”

### 좋은 질문 (MOM Test 스타일)
- “**최근에** 단위 변환 때문에 시간 잡아먹힌 적 있어?”
- “그때 **어떻게** 했어? (구글? 계산기? 엑셀?)”
- “그 방법에서 **제일 짜증 났던 점**은?”
- “비슷한 일 **얼마나 자주** 해?”
- “그 문제 때문에 **뭔가 돈** 쓴 적 있어?”

---

## 7. MOM Test 후에 해야 할 해석

인터뷰 몇 번 후, 이렇게 정리합니다.

1. **패턴**: 여러 사람이 **같은 pain**을 말했는가?
2. **행동**: 이미 **대체 수단**을 쓰고 있는가?
3. **우선순위**: 그 문제가 **Top 3 고민**인가, 그냥 “있으면 좋겠다” 수준인가?
4. **세그먼트**: **누가** 가장 아프게 겪는가?

**Go / Pivot / Stop** 판단:
- **Go**: 반복되는 pain + 행동 + 지불/노력의 흔적
- **Pivot**: 문제는 있는데, 내가 생각한 문제/고객이 아님
- **Stop**: “좋겠다”만 있고 행동·사례가 없음

---

## 8. Unit Converter 맥락에 적용하면

README의 Unit Converter는 **기술 실습**(OCP, 테스트, 설정 외부화) 프로젝트입니다. MOM Test를 붙인다면 이런 질문이 됩니다.

- “단위 변환을 **자주** 하는 사람은 누구인가?” (학생? 엔지니어? 요리?)
- “그들은 **지금** 뭘 쓰는가?” (구글, 네이버, 전용 앱, 엑셀?)
- “**어떤 상황**에서 가장 불편한가?” (현장, 수업, 해외 쇼핑?)
- “새 단위 등록, JSON/CSV 출력 같은 기능은 **실제 workflow**에 맞는가?”

→ **“기능을 더 만드는 것”**보다 **“누의 어떤 순간의 어떤 고통을 줄이는 것”**이 진짜 문제인지 먼저 확인하는 과정입니다.

## PRD가 “가짜”였던 이유

PRD는 보통 이렇게 시작합니다.

> “길이 단위 변환 **CLI**를 PRD와 테스트로 **추적 가능하게 재구현**한다.”

| PRD에 들어간 것 | Mom Test에서의 성격 |
|----------------|---------------------|
| CLI | **솔루션(채널)** — 아무도 원하지 않음 |
| 길이 3단위 | **기능 범위** — ft/in 복합 pain과 안 맞음 |
| PRD·테스트 추적 | **개발/교육 목표** — End User pain 아님 |
| 재구현 | **엔지니어링 작업** — 사용자 언어 아님 |

즉, **“무엇이 아픈가(Problem)”** 를 거치지 않고 **“무엇을 만들까(Solution)”** 로 PRD가 시작된 상태였습니다. Mom Test에서 흔히 나오는 **Solution-first PRD** 패턴입니다.

## PRD vs Problem Statement

```
[Mom Test 결과]          [PRD]
     Problem      →    Requirements
   (왜 만드는가)        (무엇을 만드는가)
        ↓                    ↓

```

**가짜 PRD:** 솔루션이 먼저 → “CLI 재구현”  
**진짜 PRD:** 문제가 먼저 → 그다음 솔루션 선택

Mom Test 결과, **고객이 두 종류**라 PRD도 갈라져야 합니다.

- 비목표: CLI 강제, OCP 실습, PRD 추적 (이건 제품 PRD가 아님)

### 2) 실습/교육 PRD (README·6시간 워크샵 기준)

**Problem:**

> 하드코딩된 변환 스크립트는 요구·테스트·설정과 연결되지 않아, 설계·TC·확장성을 연습하기에 부적합하다.

- **고객 = 학습자/조직**, 제품 사용자 아님을 PRD에 명시

## 2. OCP / SRP 적용 원칙

### SRP — “한 클래스/모듈 = 한 변경 이유”

| 모듈 | 단일 책임 |
|------|-----------|
| `domain/models` | 값 객체·결과 구조 정의 |
| `input/parser` | 문자열 → 구조화 데이터 |
| `input/validator` | 비즈니스 규칙 검증 |
| `conversion/registry` | 단위 정의 저장·조회 |
| `conversion/engine` | 기준단위 경유 수치 변환 |
| `config/*_loader` | 파일 → registry 초기화 |
| `output/*_formatter` | `ConversionResult` → 문자열 |
| `app/service` | 유스케이스 조합 (테스트 진입점) |
| `app/cli` | 사용자 I/O·옵션 파싱만 |

### OCP — “확장에는 열려 있고, 수정에는 닫혀 있다”

| 확장 시나리오 | 수정 없이 추가 | 수정이 필요한 곳 (최소) |
|---------------|----------------|-------------------------|
| 단위 추가 (feet → mile) | `config/units.json` 또는 런타임 `registry.register()` | **없음** (engine/parser/formatters 불변) |
| 출력 포맷 추가 (Markdown) | `output/markdown_formatter.py` + registry/factory 등록 | factory 등록 1곳만 |
| 설정 포맷 추가 (TOML) | `config/toml_loader.py` 구현 | loader 선택 wiring 1곳 |
| 검증 규칙 추가 (max value) | `validator`에 rule 클래스 추가 | validator 조합 |
| CLI 명령 추가 (register) | `cli` 서브커맨드 | `cli.py`만 |

### 핵심 인터페이스 (개념)

```python
# conversion/protocols.py
class OutputFormatter(Protocol):
    def format(self, result: ConversionResult) -> str: ...

class ConfigLoader(Protocol):
    def load(self, path: Path) -> UnitRegistry: ...
```

`ConversionEngine`은 **registry만** 의존 → 단위 종류를 몰라도 동작 (meter hub는 registry/UnitDefinition에 캡슐화).
